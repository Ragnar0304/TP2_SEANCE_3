**Groupe :** KOUASSI KOUAKOU YANN LOIC - KANGAH KOUAME LUC MARTIAL - FOFANA CHEIKH

**Environnement :** VM `ubuntu-srv1` (Ubuntu 26.04.1 LTS, noyau 7.0.0-42-generic) sous VirtualBox 7.2.20, pilotée depuis PowerShell sur l'hôte Windows. Docker 29.1.3.

**Image publiée :** https://hub.docker.com/r/ragnar0304/api-fil-rouge (étiquette `1.1`)

## Remarque sur le déroulement

L'ensemble du TP a été réalisé depuis PowerShell sur l'hôte Windows, en se connectant à la VM par SSH (`ssh -p 2222 etudiant@127.0.0.1`), grâce à la redirection de port 2222 vers 22. La VM est démarrée en mode headless, sans fenêtre graphique, comme le prévoit le TP. Cette méthode permet aussi le copier-coller des commandes.

### Questions

**1. Quelle version de Docker est installée ? Quel noyau est utilisé ?**

Docker 29.1.3 (client et serveur, API 1.52), avec containerd 2.2.2 et runc 1.4.0. Le noyau est `7.0.0-42-generic`, celui d'Ubuntu 26.04.1 LTS. Le pilote de stockage est `overlayfs` et les cgroups sont en version 2 avec le pilote `systemd`.

**2. Pourquoi appartenir au groupe `docker` équivaut-il presque à être administrateur ? Quelle précaution sur un serveur partagé ?**

Le groupe `docker` donne accès au démon Docker, qui tourne en root. Un membre peut lancer un conteneur qui monte n'importe quel dossier de l'hôte (par exemple `-v /:/hote`) et y lire ou écrire avec les droits de root. Sur un serveur partagé, il ne faut donc donner ce groupe qu'à des personnes de confiance, ou utiliser un mode sans privilèges (Docker rootless, Podman).

### Questions

**1. Quelles sont les quatre étapes réalisées par Docker d'après le message de `hello-world` ?**

1. Le client Docker contacte le démon Docker.
2. Le démon télécharge l'image `hello-world` depuis Docker Hub (version amd64).
3. Le démon crée un nouveau conteneur à partir de cette image, qui exécute le programme produisant le message.
4. Le démon envoie cette sortie au client, qui l'affiche dans le terminal.

**2. Le conteneur `web` et la VM ont-ils la même distribution ? Le même noyau ? Expliquez.**

Non pour la distribution : le conteneur est sous Debian GNU/Linux 13 (trixie), la VM sous Ubuntu 26.04.1 LTS. Oui pour le noyau : `uname -r` donne `7.0.0-42-generic` des deux côtés. Un conteneur n'embarque pas de noyau : il utilise celui de la machine hôte. L'image ne fournit que les fichiers de la distribution (bibliothèques, outils) et l'application.

**3. Les processus Nginx du conteneur apparaissent-ils dans `ps aux` sur la VM ? Qu'est-ce que cela montre ?**

Oui. Le processus `nginx: master process nginx -g daemon off;` apparaît dans `ps aux` sur la VM avec le PID 2896, le même que dans `docker top web`, et son processus fils `nginx: worker process` (PID 2979) aussi. Un conteneur n'est donc pas une machine virtuelle : c'est un ou plusieurs processus ordinaires de l'hôte, isolés par les espaces de noms (namespaces) et limités par les groupes de contrôle (cgroups).

**4. Quel est le chemin d'une requête du navigateur de l'hôte jusqu'à Nginx ? Quelles redirections de port ?**

Navigateur Windows → `127.0.0.1:8080` sur l'hôte → redirection NAT de VirtualBox (règle `web`, port hôte 8080 vers port invité 8080) → port 8080 de la VM → redirection de port de Docker (`-p 8080:80`) → port 80 du conteneur `web` → Nginx. Il y a donc deux redirections successives : une de VirtualBox, une de Docker.

**5. Pourquoi la page modifiée a-t-elle disparu après `docker rm` ? Que change `-v` ?**

La modification avait été écrite dans la couche inscriptible propre au conteneur, qui est supprimée avec lui. Le nouveau conteneur repart de l'image d'origine, d'où le retour à « Welcome to nginx! ». Avec `-v ~/site:/usr/share/nginx/html:ro`, le dossier `~/site` de la VM est monté dans le conteneur : les données vivent en dehors du conteneur et survivent à sa suppression.

### Questions

**1. Quel rapport de légèreté et de rapidité entre conteneur et VM ? Vos mesures confirment-elles le cours ?**

Mémoire : 453 Mi pour la VM contre 2,7 MiB pour le conteneur Nginx, soit environ 170 fois moins. Démarrage : 96 s pour la VM contre 3,4 à 4,1 s pour un conteneur Alpine, soit environ 25 à 30 fois plus rapide. Taille : 13 Mo pour Alpine contre un disque de 11,21 Go pour la VM (environ 5,3 Go utilisés). Les mesures confirment l'ordre de grandeur du cours. Les temps de conteneur sont cependant plus longs que les valeurs habituelles (moins d'une seconde), car la VM dispose de peu de ressources (1,6 Gi de mémoire) et tourne sur un poste hôte déjà chargé.

**2. Pourquoi le premier `time docker run` est-il plus long que le second ?**

Au premier lancement, Docker prépare la couche inscriptible, et les fichiers de l'image ne sont pas encore dans le cache disque de la VM. Au second, ils y sont déjà, ce qui explique l'écart observé (4,087 s contre 3,359 s).

**3. Citez un cas où vous choisiriez quand même une VM.**

Quand il faut un système d'exploitation ou un noyau différent de celui de l'hôte (par exemple Windows sur un serveur Linux), ou une isolation forte entre locataires qui exécutent du code non fiable. Une VM a son propre noyau, alors que les conteneurs partagent celui de l'hôte.

## Partie 3 – Conteneuriser l'API fil rouge

### 3.1 Le code de l'API

```bash
mkdir -p ~/api && cd ~/api
cat > app.py <<'EOF'
import os
import socket
from flask import Flask, jsonify

app = Flask(__name__)

@app.get("/")
def accueil():
    return jsonify(
        message="API fil rouge",
        binome=os.environ.get("BINOME", "inconnu"),
        conteneur=socket.gethostname(),
    )

@app.get("/sante")
def sante():
    return jsonify(statut="ok")

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=5000)
EOF
echo "flask>=3,<4" > requirements.txt
```

Les deux fichiers sont créés sans message de sortie ; le prompt `etudiant@ubuntu-srv1:~/api$` revient simplement après `echo "flask>=3,<4" > requirements.txt`.

### 3.6 Ajouter la route `/version` et construire `api:1.1`

```bash

mv new.py app.py
tail -n 12 app.py
docker build -t api:1.1 .
```

### Questions

**1. Quelle est la taille de `api:1.0` ? Combien de couches dans `docker history` ? Lesquelles viennent de votre Dockerfile ?**

`api:1.0` occupe 198 Mo sur disque (48,3 Mo de contenu compressé). `docker history` montre d'abord les couches issues de notre Dockerfile : `WORKDIR /app` (8,19 ko), `COPY requirements.txt` (12,3 ko), `RUN pip install` (15,3 Mo), `COPY . .` (20,5 ko), `EXPOSE 5000` (0 o) et `CMD ["python", "app.py"]` (0 o), soit 6 instructions, dont 2 qui ne sont que des métadonnées. Viennent ensuite les couches de l'image de base `python:3.12-slim` (celles marquées « il y a 3 jours »).

**2. Pourquoi copier `requirements.txt` et installer les dépendances avant de copier le code ? Appuyez-vous sur les lignes `CACHED`.**

Docker met en cache chaque instruction tant que ses entrées ne changent pas. En plaçant `COPY requirements.txt` et `RUN pip install` avant `COPY . .`, une modification de `app.py` ne reconstruit que la dernière couche. Au build de `api:1.1`, les lignes `[2/5] WORKDIR`, `[3/5] COPY requirements.txt` et `[4/5] RUN pip install` sont marquées `CACHED` : seule `[5/5] COPY . .` est refaite. Le gain est net : le premier build de `api:1.0` a duré 70,8 s, dont 30,5 s pour `pip install`, alors que le build de `api:1.1` ne reconstruit que les couches modifiées et dure quelques secondes (4,8 s observées pour un build où les couches étaient en cache).

**3. Que renvoie le champ `conteneur` pour les trois copies ? Quelle caractéristique du cloud (séance 1) est illustrée ?**

Chaque copie renvoie un identifiant différent (`6b32b99ee08f` et `d64a7a55a4bf` dans la sortie ci-dessus, `e4914b326343` pour la troisième copie : ce sont les noms d'hôte des conteneurs, c'est-à-dire les 12 premiers caractères de leur identifiant), alors que l'image est la même. On voit qu'une même image peut être lancée en plusieurs exemplaires en quelques secondes : c'est l'élasticité rapide (passage à l'échelle horizontal) du cloud.

**4. Pourquoi passer le nom du binôme par `-e` plutôt que dans le code ? Quel lien avec les secrets ?**

La configuration est séparée de l'image : la même image sert pour tous les environnements, sans reconstruction, et on change la valeur au lancement. Cela évite aussi d'écrire dans le code ou dans l'image des informations propres à un utilisateur ou à un environnement, car une image est partagée et conserve son historique de couches. Pour les secrets (mots de passe, jetons), le principe est le même : ils ne doivent jamais être écrits dans le code ou dans l'image, mais fournis à l'exécution, idéalement via un gestionnaire de secrets plutôt qu'une simple variable d'environnement.
